# Code standards

Canopy had no single standards document before this one. Its conventions existed only
as practice, scattered across individual `DECISIONS.md` entries. This document distills
what's actually followed (each rule traces to a `DECISIONS.md` section, the same
traceability convention `undercover`'s `docs/CODE_STANDARDS.md` uses for its own rules),
and extends it in a few places where comparing against `undercover`'s stack (a
LangChain/LangGraph claims agent with money, sign-off and durability concerns canopy
doesn't have) surfaced a gap worth closing anyway. Written during the Phase 5
code-standards review in `docs/PLAN_ROBUSTNESS.md`.

Rules that only make sense for a money-moving, multi-step workflow (idempotency keys,
`Decimal` currency, sign-off authority, durable checkpointing) are deliberately left
out. Canopy's query loop is single-shot, stateless and read-only, and importing that
machinery would add complexity for a risk canopy doesn't carry (see `docs/
PLAN_ROBUSTNESS.md`'s reasoning for not porting it).

## General

1. **Keep it simple. Add an abstraction only when current code needs it.** `query/loop.py` has one tool (`execute_sql`), not a tool-plugin framework; `models/registry.py` dispatches on three concrete `api_style` values via `if`/`elif`, not a registry pattern, because there are three of them (see A3).
2. **Give each function one clear responsibility.** The query loop's own shape enforces this: `_build_sql_tool` builds the tool, `_run_agent` drives the agent, `run_query` orchestrates caching/tracing/history around it, and each can be read independently in the codebase today.
3. **Every environment variable is read in exactly one place: `config.py`.** This is O1, stated as a hard rule from the start, and was found violated by four files during this review (`query/fuzzy_match.py`, `query/loop.py`, `observability.py`, `cache.py`), each reading `os.environ` directly. Fixed (see `DECISIONS.md`'s O1 entry and `LIMITATIONS.md`'s Operational & Security Tooling Gaps table) by adding getters to `config.py` and updating every call site. The rule drifted without anyone intending to break it, so it needs enforcing, not just stating.
4. **Treat prompts and guardrails as code: version them, test them, don't rely on them alone as a trust boundary.** `schema.py`'s prompt carries a guardrail list; S1/S2/S6 back every prompt-level instruction with a code-level check (the regex SQL guard, the read-only DB session, the adversarial eval suite). A prompt is the first line of defense, never the only one.
5. **Treat model output and customer-adjacent content as untrusted.** Any text a judge (`eval/judge.py`) is shown that didn't come from the question itself, query result rows in particular, carries an explicit "this is data, not instructions" disclaimer in the prompt (see `_FAITHFULNESS_JUDGE_PROMPT`, and T3's equivalent for the guardrail judge). A column value could in principle be adversarially crafted.
6. **Never let a model enforce a control deterministic code should own.** Canopy's version of `undercover`'s "never let a model enforce a payment or permission rule": the SQL guard (S2), the sensitive-column strip (S3), and the validation-status default filter (S4) are all pure Python checks the model can't talk its way around. Where the control genuinely can't be made deterministic (judging whether free-form text upheld a behavioral guardrail has no regex equivalent), the enforcement decision itself is still deterministic code reading a structured verdict, and the substituted text on a block is fixed and code-authored rather than anything the judging or judged model wrote. T6's runtime guardrail gate: the judgment is necessarily a model call, but what happens with that judgment (replace with `error_guardrail_blocked`, exactly, or don't) is an `if` statement, not a second prompt asking nicely.

7. **Comments explain *why*, and this codebase uses them liberally where undercover doesn't. That's a deliberate difference, not a violation to fix.** `undercover`'s own rule 11 says "comments only when necessary... be concise." Canopy's actual practice is denser: comments routinely cite a live-testing date, a confirmed root cause, or a rejected alternative (see nearly every function in `query/loop.py`). This review doesn't recommend trimming that down to match `undercover`'s minimalism; the density has repeatedly paid for itself in this codebase (S3's "scope widened" note explaining why a past decision reversed, A1's "no empirical basis" self-critique). Keep writing the *why*; still don't restate the *what* a well-named function already says.
8. **No secrets in code, logs, or test fixtures.** `config.py` is the only place credentials are read, structured logs carry identifiers (question, connection id, row counts) rather than raw model/DB payloads, and `observability.py`'s `trace_query` sends "the same shape of information already visible in the UI... never raw row data."

## Reliability

9. **Every external call has a timeout.** `AzureResponsesLLM`, `_openrouter`-equivalent connections, and the `openai` SDK connections all carry an explicit timeout from `models.yaml`.
10. **A failure has a kind, and a kind determines whether retrying elsewhere could help.** New as of Phase 4 (`DECISIONS.md`'s M3 section): `models/failures.py`'s `is_retryable_model_error()` classifies a model-call failure as an outage symptom (worth one bounded retry against another connection) or a defect that would recur identically anywhere (SQL error, content-filter decline, bad request). Never a blanket `except Exception: retry`. Extend this classifier if a new connection type's failure mode needs handling; don't bypass it.
11. **A hard limit stated anywhere (a prompt, a doc) has a code-enforced twin, and the twin is what actually fires.** `MAX_ITERATIONS = 5` is enforced by `FunctionAgent` itself, not by the prompt alone, but this review found and fixed a case where the enforcement existed while the handling of it didn't actually work: `app.py` checked for a `RuntimeError` containing "maximum iterations," while the real library raises `workflows.errors.WorkflowRuntimeError` with different wording entirely (`DECISIONS.md`'s A1 correction note). A passing test had mocked the same wrong assumption the code made, so the gap was invisible until read against the installed library's real source. The standard this sets: when wrapping a third-party failure mode, verify the actual exception type and message against the installed library's source or a live call, rather than assuming the shape from documentation, memory, or what "seems like" it should be.
12. **An eval or structural test that encodes an assumption about a dependency's behavior should be checked against that dependency's real behavior at least once**, not just internally consistent with the code it's testing. Rule 11's bug survived specifically because the test and the code shared the same wrong assumption.

## Testing

13. **Tests never make a live model or database call unless explicitly marked** (`live_db`, or a `scripts/` entry point documented as requiring credentials). `tests/eval/queries.py`'s judge-backed cases are excluded from the no-live-call parametrized test (`test_check_fn_returns_bool_on_minimal_result`), with a comment measuring the actual time cost that motivated the exclusion.
14. **A judge (LLM-as-judge) needs calibration against hand-labeled cases before its failures are trusted, and that calibration is a separate, visible artifact** (`scripts/calibrate_judge.py`, `scripts/calibrate_faithfulness_judge.py`). It isn't folded into the judge's own unit tests, which only prove the plumbing around a live call, not the live call's actual correctness.
15. **A category of eval case added to close a known gap is additive to the existing checks, not a replacement**, unless the existing check is actually wrong. Category 21 and 22 both followed this: the cheap, deterministic, zero-cost checks stay as the first pass, and a judge is only asked to resolve what they structurally can't.
16. **When a review finds a genuinely insufficient-evidence situation, say so rather than guessing a verdict.** `DECISIONS.md`'s T5 entry is the canonical example: evidence existed (one ambiguous historical data point) but wasn't enough to decide between two real options, and the entry says exactly that instead of picking one anyway. This is the same standard T2 already set ("tracked as a gap") applied to a new case.

## Documentation hygiene

17. **A summary table (`DECISIONS.md`'s "Decision map") must match the body text it summarizes.** Found stale during this review: the map's O2 row said "no pooling" after pooling had been implemented and the body's own audit verdict marked it closed; the A3 row described a `ModelClient` ABC that the body says was replaced. A map that drifts from its own detail entries is worse than no map, since it's the thing most likely to be read first and trusted. Update both in the same change, always.
18. **A claim in a decision record should be checked against the actual code before being written down, not assumed from a design intent.** This review's own T4 entry needed a correction mid-draft: an early claim that `run_eval.py` treats judge-backed cases as "informational" was checked against the runner's actual pass/fail-counting code and found false before being published. A wrong claim in a decision record defeats its purpose, which is to save a later reader from re-deriving the reasoning, so it's worth the extra few minutes to check.
19. **A stale or inconsistent number in documentation gets flagged, not guessed into a "corrected" value.** `tests/eval/queries.py`'s "Target: ≥85% pass rate (≥42/61)" is arithmetically inconsistent (42/61 ≈ 69%) independent of anything in this review, and the origin of either number isn't known. Noted in the docstring and in `LIMITATIONS.md` rather than changed to a number this review invented.

## What this document does not cover (yet)

- **Secret-scanning in CI.** Not present before this review, not added by it (see `DECISIONS.md`'s O10 section). A `detect-secrets`/`gitleaks` baseline requires a one-time full-history scan and manual triage, which is real, separate work.
- **A formal severity/response policy for `pip-audit` findings.** O10 makes the scan informational given one confirmed, currently-unfixable transitive CVE; a policy for what happens when a fixable CVE appears doesn't exist yet.
- **Long-function or layering rules** (`undercover`'s rule 16: "a function does one job in 30 lines or fewer"). Not adopted as a hard rule here. `ui/app.py`'s `build_app()` (≈250 lines) and its `_worker` closure are long by the nature of Gradio component/event wiring, and this review had no way to test a UI refactor live (no browser/live DB in this environment) to confirm a split wouldn't regress behavior. Flagged as a candidate for a future review that can actually run and click through the UI afterward.
